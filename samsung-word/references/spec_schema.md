# spec.json 스키마

`scripts/build_doc.py`에 넘기는 JSON 스펙의 구조입니다.

```json
{
  "doc_type": "general",
  "title": "OO시스템 장애 보고",
  "meta": "'24. 09. 10(월) 고객서비스팀",
  "summary": {
    "purpose": "장애 원인과 재발 방지 대책 공유",
    "claim": "네트워크 장비 이중화 미비로 장애 발생",
    "conclusion": "이중화 구성 및 모니터링 강화 필요"
  },
  "sections": [
    {
      "level": 1,
      "text": "장애 개요",
      "children": [
        {
          "level": 2,
          "text": "발생 일시 및 영향",
          "children": [
            {"level": 4, "text": "서비스 접속 장애 42분 발생, 영향 고객 1.2만 명"},
            {
              "table": {
                "caption": "<시스템 장애 발생 로그>",
                "headers": ["구분", "시각", "내용"],
                "rows": [
                  ["장애 발생", "14:02", "접속 불가 시작"],
                  ["복구 완료", "14:44", "정상화 확인"]
                ],
                "source_note": "표 설명 or 출처 표시"
              }
            },
            {
              "level": 4,
              "text": "복구 소요 42분",
              "after_table": true,
              "notes": [{"marker": "ㄴ", "text": "SLA 기준 30분 초과"}]
            }
          ]
        }
      ]
    },
    {
      "level": 1,
      "text": "재발 방지 대책",
      "children": [
        {
          "level": 2,
          "text": "조치 사항",
          "children": [
            {
              "level": 4,
              "text": "핵심 장비 이중화 적용, 4주 내 완료",
              "children": [
                {"level": 5, "text": "1차: 코어 스위치, 2차: 방화벽"}
              ]
            }
          ]
        }
      ]
    }
  ]
}
```

## 필드 설명

- `doc_type`: `"general"`(일반 양식, 기본 여백) 또는 `"shared"`(전사 공유 양식 — 목차 페이지, 요약 페이지, 최소 여백 자동 적용). 목차는 1레벨 `sections` 제목들을 스크립트가 자동으로 모아 네모 박스(가운데 정렬) 안에 번호와 함께 실제 텍스트로 채운다 — Word 필드 코드가 아니므로 별도 업데이트 없이 바로 보인다
- `title`: 문서 제목 (20pt, 굵게, 가운데 정렬)
- `meta`: 제목 바로 아래, 우측 정렬로 들어가는 날짜·작성 부서 한 줄 (예: `"'24. 09. 10(월) 고객서비스팀"`). 생략 가능
- `end_marker`: 문서 맨 끝에 관용적으로 붙이는 `- 이 상 -` 표시. 기본값 `true` (안 붙이려면 `false`로 명시)
- `summary`: `doc_type: "shared"`일 때만 사용. 목적·주장·결론을 요약 페이지로 자동 생성
- `sections`: 레벨 구조 트리
  - `level`: 1~5 정수, 또는 `"note"` — 레벨별 기호·폰트 크기·굵기·간격은 자동 적용 (가이드 표 그대로)
    - 1레벨: `1.`, `2.` … / 16pt Bold
    - 2레벨: `□` / 14pt Bold
    - 3레벨: `1)`, `2)` … / 14pt
    - 4레벨: `-` / 14pt
    - 5레벨: `·` / 12pt
    - `note`: `ㄴ`/`ㄱ` / 9pt (Shift+Enter로 상위 문단에 붙임 — 별도 문단 아님)

    **레벨 선택 기준**: `□`(2레벨)는 **제목/소제목**에만 쓴다 — 그 항목 자체가
    실제 서술 내용(예: "단기 조정 국면이나 AI 메모리 수요 기반 중장기 상승
    여력 유효" 같은 결론·판단 문장)이라면 제목이 아니라 **내용**이므로 `□`가
    아니라 `-`(4레벨)를 쓴다. 예:
    ```
    (X) □ 단기 조정 국면이나 AI 메모리 수요 기반 중장기 상승 여력 유효
    (O)  - 단기 조정 국면이나 AI 메모리 수요 기반 중장기 상승 여력 유효
    ```
    "종합 의견", "결론", "조치 사항"처럼 그 아래 내용을 묶는 제목만 `□`를 쓰고,
    실제 판단·설명·수치가 담긴 문장은 항상 `-`(4레벨) 이하를 쓴다.
  - `text`: 문장. **개조식**으로 작성 (서술형 종결어미 대신 명사형/명사구로 마무리). 형용사·부사 대신 **수치**를 포함시킬 것
  - `children`: 하위 항목 배열. **중요**: 들여쓰기는 레벨 번호가 아니라 이 `children`
    안에 몇 단계 들어가 있는지(실제 트리 깊이)로 정해진다. 그래서 3레벨을
    건너뛰고 2레벨 밑에 바로 4레벨을 넣어도, 그 4레벨 항목을 2레벨 항목의
    `children` **안에** 넣기만 하면 부모보다 한 칸만 더 들여써진다. 반대로
    같은 레벨의 항목을 나란히 나열하고 싶을 때만 같은 배열에 형제로 둔다 —
    형제로 두면 들여쓰기가 같아진다
  - `after_table`: 이 항목이 표 바로 뒤에 오면 `true` — 줄 앞간격 8pt 규칙 적용
  - `notes`: 이 항목에 붙는 주석 라인 배열 (Shift+Enter, 꺾임기호 `ㄴ`/`ㄱ`)
  - `table`: `{"headers": [...], "rows": [[...], ...], "col_widths_cm": [...], "caption": "<표 제목>", "source_note": "표 설명 또는 출처"}` — 데이터 표현은 표 우선, 그래프·이미지는 넣지 않음. `caption`은 표 위에 가운데 정렬로, `source_note`는 표 아래에 `※ ...` 형식(9pt)으로 자동 표시
    - 표 셀은 헤더 포함 **모두 가운데 정렬**로 통일한다. 헤더 행은 밝은
      회색 배경(#D9D9D9) + 검정 굵은 글씨로 자동 표시되어 데이터행과 구분된다
      (스크립트가 알아서 처리, spec에서 따로 지정 안 해도 됨)
  - `wrap_lines`: 이 항목의 내용이 길어서 둘째 줄로 이어질 때 쓰는 배열.
    각 줄은 **별도 문단(진짜 Enter)** 으로 추가되고, 기호 없이 첫째 줄 텍스트
    시작 위치(depth칸 들여쓰기 + 기호·공백 2칸)에 맞춰 자동으로 들여써진다
    (depth 1이면 3칸, depth 2면 4칸 등 — 직접 계산할 필요 없음). Shift+Enter가
    아니라 별도 문단인 이유는, 같은 문단 안에서 줄바꿈하면 실제 Word의 폰트 폭
    계산 차이로 앞부분이 다시 자동 줄바꿈될 때 들여쓰기가 깨지기 때문이다.
    `notes`(꺾임기호 주석)와는 다른 용도 — `wrap_lines`는 같은 문장의 연속,
    `notes`는 본문에 대한 부연 설명/출처다

## 개조식 작성 체크 (spec 채우기 전 스스로 점검)

| 서술형 (X) | 개조식 (O) |
|---|---|
| 고객은 제품 선택 시 기능 요소를 가장 중요하게 고려하며, 성능 테스트는 필수가 아니라고 판단 중임 | 제품 선택 시 고객은 기능 요소가 중요, 성능 미고려 |
| 제품 성능 향상 추진 | 제품 성능 30% 향상 추진 |

강조가 필요한 핵심 단어/수치는 `add_emphasis()`로 밑줄+Bold 처리하거나,
텍스트에 표시해두고 별도 후처리하는 방식을 사용합니다 (기본 spec 흐름에는
강조 필드가 없으므로, 강조가 많이 필요한 문서는 `build_from_spec` 대신
`scripts/build_doc.py`의 함수들을 직접 import해 문단 단위로 조립하세요).
